# 直播源是怎么维护的（源维护说明）

> 这份文档同时回答两个问题：**普通用户**为什么 HTV 不用自己找源；**想参与维护的贡献者**，
> 怎么把你的反馈变成下一轮更新里「修好的频道」。

## 一、HTV 的源从哪来

HTV 客户端不内置固定源列表，播放列表由服务端每日生成、下发，流程是：

```
采集（多个来源、多协议）
   ↓
频道名归一化（全半角、连字符、超清/4K 后缀统一，避免「CCTV.5综合」「CCTV-5」被当成两个频道）
   ↓
连通性体检（并发探测每条源，测响应速度与可播性，超时/死链标记降权）
   ↓
排序合并（健康源靠前、历史坏源退避，同频道保留多个可用源互为备份）
   ↓
下发 iptv4.json（客户端按顺序播放，坏源自动跳下一个）
```

这条管线每天自动跑一轮，所以：

- **你不需要自己找源**——源挂了通常下一轮更新就自动修复
- **多源频道更抗风险**——同一频道保留多条源，一条挂了客户端会自动切下一条

## 二、客户端这一侧做了什么

服务端体检是「探测」，客户端是「真实播放环境验证」，两层互补：

| 机制 | 触发条件 | 动作 |
| --- | --- | --- |
| 自动换源 | 播放出错 | 立即切到下一个源 |
| 卡顿切源 | 缓冲中断 2 秒未恢复 | 立即切源 |
| 起播停滞检测 | 起播缓冲 4 秒无进展 | 判死并切源 |
| 源健康度记忆 | 播放失败 | 本地记下坏源，指数退避（10 分钟 → 24 小时），成功即恢复 |

也就是说：**你在真实环境里遇到的坏源，App 会当场绕开，并在之后的播放里主动避开它。**

## 三、失效频道怎么反馈（重点）

在 [Discussions 的「源失效反馈」分类](https://github.com/HTWMedia/HTV/discussions)发帖，或到 QQ 群（一群 2166024531 / 二群 1067526818）反馈，**按这个格式写**：

```
频道名：CCTV-5
现象：黑屏 / 一直转圈 / 卡住不动 / 提示播放失败
所在地区 + 网络：山东 · 联通宽带
App 版本：v6.0.0
```

为什么这么要求：

- **地区很关键**——不少源是分省 IPTV 出口，同一个频道在你那里挂、在我这里是好的
- **现象决定处理方式**——黑屏多为源死了；转圈可能是并发限流；特定时段才卡可能是高峰限速
- 符合格式的反馈会进自动体检队列，**下一轮更新生效**，不需要等新版本

## 四、想贡献源 / 改进体检逻辑

- 有稳定可用的公开源想推荐：欢迎发到 Discussions「源失效反馈」分类，注明「推荐新源」
- 体检 / 归一化 / 排序逻辑的改进：见 [CONTRIBUTING.md](../CONTRIBUTING.md)
- 红线：**不要在仓库任何地方粘贴付费源、内网 IPTV 地址或需要鉴权的链接**

## 五、常见疑问

**为什么同一个频道画质时好时坏？**
不同源的码率不同，自动换源后画质会跟着变。多源互为备份是稳定优先的设计取舍。

**为什么有的地方台只有别的省有？**
频道按省级区分下发，港澳台及少数地区默认使用北京的源。如果你所在的省缺频道，反馈给我们补。

**多久更新一次？**
服务端每日自动更新，客户端打开即取最新列表，App 本身不需要频繁升版本。
